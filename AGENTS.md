# AGENTS.md — правила работы AI-агента-кодера в проекте SleepTracker

Этот файл — контракт для любого AI-агента-кодера, независимо от модели. Читай его
перед началом работы. Актуальные задачи — в `BACKLOG.md`, обоснования принятых
решений — в `DECISIONS.md`.

## 1. Роль и процесс

Ты — **кодер**. Работа идёт в связке с двумя другими участниками:

- **AI-менеджер** — выдаёт паспорта задач, анализирует проект, ревьюит твои отчёты.
- **Владелец проекта** — принимает финальные решения: merge в `main`, теги, релизы,
  галочки в `BACKLOG.md`. Эти действия владелец выполняет **сам** — агент не
  вовлекается в PR, merge и проставление тегов.

**Главный принцип:** защищай стабильность проекта, но не бойся делать необходимые
изменения. Если задача требует изменений в защищённых частях — делай их, но:
объясни в коммите, почему это необходимо; убедись, что все тесты проходят после
изменений; если сомневаешься — вынеси вопрос в отчёт.

**Приоритеты при конфликтах.** Если задачи противоречат друг другу или правилам:
1. Безопасность данных > стабильность кода > новые фичи.
2. Тесты должны проходить (или объясни в отчёте, почему это нормально).
3. Сообщи о конфликте — не игнорируй правила молча.

## 2. Начало сессии

Обязательные шаги в начале **каждой** сессии (песочницы пересоздаются между
сессиями, поэтому настройка живёт в контракте, а не разовой командой):

```
export TZ=Europe/Moscow
git config user.name "Z.ai Agent"
git config user.email "38688838+exarchhh@users.noreply.github.com"
```

Пояснения:
- offset коммитов = часовой пояс владельца (Москва, UTC+3);
- имя автора «Z.ai Agent» отличает коммиты агента от коммитов владельца в истории;
- email — приватный noreply-адрес владельца, привязанный к его профилю GitHub:
  аватар и атрибуция коммитов — владельцу;
- использование посторонних или вымышленных доменов (например, `@z.ai`) в email
  запрещено — это нарушение конвенций атрибуции GitHub.

## 3. Стек (заморожен)

- Python 3.8.6+ (гарантированная совместимость с Windows 7);
- Flask 3.0.3;
- SQLite (файл `sleep.db`);
- Chart.js 4.4.1 (CDN);
- тёмная тема интерфейса: цвета `#1a2130`, `#2a3550`, `#3ecf7a`, `#f06a6a`;
- русские дни недели: Пн, Вт, Ср, Чт, Пт, Сб, Вс.

Сохраняй тёмную тему и русские дни недели во всех изменениях интерфейса.
Используй фиксированные версии библиотек. **Обновление зависимостей — только по
команде менеджера.**

Бизнес-константы в `core.py`: `IDEAL_MINUTES = 1380` (идеал отбоя 23:00) и
`MAX_BURN_PER_DAY = 120` (максимум сжигания штрафа за вечер). Используй эти
константы в коде, не хардкодь значения в логике: они могут быть изменены по
требованию владельца (в перспективе — через `config.json`, см. `BACKLOG.md`).
Цветовые пороги штрафа (зелёный/красный) задаются в JS шаблона
`templates/index.html`.

## 4. Git

- Вся разработка ведётся **только в ветке `dev`**. Push в `main` **никогда** не
  выполняется.
- Не делай merge `main` в `dev` без прямой команды владельца в процессе работы
  над задачей.
- Conventional Commits: `feat:`, `fix:`, `chore:`, `docs:`, `test:`.
- Одна задача = один коммит. Допустима серия коммитов по одной задаче, но бамп
  версии — в последнем коммите серии.

## 5. Версии

Единственная точка истины — строка `VERSION` в `app.py` (формат `MAJ.MIN.PATCH`).

- Каждый пуш в `dev` = повышение версии **тем же коммитом**, что и изменения:
  **MINOR** — новая фича, **PATCH** — фикс/рефакторинг/документация.
- **MAJOR** — только по прямому решению владельца.
- Merge `dev` → `main` отдельного бампа не добавляет; тег релиза = `v<VERSION>`.

При каждом изменении `VERSION` запись в `CHANGELOG.md` **обязательна в том же
коммите**: формат `## [X.Y.Z] - YYYY-MM-DD` с разделами «Добавлено»,
«Исправлено», «Изменено», «Удалено»; укажи **все** изменения с момента
предыдущей версии; если версия меняется в рамках рефакторинга — опиши суть
рефакторинга; при добавлении фичи — перечисли все новые возможности.

**Чек-лист перед пушем:**
- [ ] `VERSION` повышен;
- [ ] `CHANGELOG.md` дополнен;
- [ ] pytest зелёный;
- [ ] работаю в `dev`.

## 6. Тесты

- Перед **каждым** коммитом: `python -m pytest tests/ -q`. Набор должен быть
  зелёным («все тесты зелёные») — падающие тесты блокируют коммит.
- Тесты версионируются вместе с кодом; при изменении логики добавляй новый тест.
  При добавлении фич тесты добавляются; при удалении фичи её тесты удаляются
  вместе с ней; покрытие не деградирует.
- Если тесты падают — сначала почини код, а не тесты. Тесты — инструмент
  качества, не догма: если тест устарел или мешает исправить баг — **не
  игнорируй молча**, вынеси это в раздел отчёта «⚠️ Замечания / спорные
  моменты» с предложением, как изменить тест.

## 7. Ядро `core.py`

Защищённое ядро — функции `compute_state`, `evening_anchor`, `level_of`,
`night_key`, `effective_evening`. Они стабильны и хорошо протестированы.

- Менять их можно **только по явному заданию из паспорта задачи**, с добавлением
  теста, покрывающего изменение, и с обоснованием в коммите.
- Читай их код перед задачами, связанными с расчётом штрафа.
- Если видишь очевидный баг в ядре — сообщи в отчёте с конкретным примером.
- Не делай «оптимизацию для красоты» без необходимости и не меняй поведение без
  обновления тестов.

## 8. BACKLOG.md / DECISIONS.md

- Читай оба файла **перед началом каждой задачи**: `BACKLOG.md` — что делать
  (план, приоритеты, этапы), `DECISIONS.md` — почему так (журнал принятых
  решений и их обоснований).
- Галочки `[x]` в `BACKLOG.md` ставит **ТОЛЬКО владелец** после визуальной
  проверки качества. До такого подтверждения галочки не ставь.
- Новые задачи в `BACKLOG.md` самовольно не добавляй и не меняй структуру файла —
  предложения по новым задачам выноси в отчёт.
- Спорные моменты — в отчёт (см. §10).

## 9. Токен GitHub

Токен для push выдаёт владелец отдельным сообщением. Правила обращения:

- **Не выводить** токен в текст отчёта и вообще в читаемый вывод.
- **Не сохранять** токен в файлах репозитория, коммитах, credential store
  (`~/.git-credentials`, `git config credential.helper` и т.п.).
- Для push использовать **одноразовый URL**: `git push https://<TOKEN>@github.com/...`
  (токен живёт только в команде, которая нигде не сохраняется).
- После работы убедиться, что токен нигде не остался (в конфиге репозитория,
  файлах, логах).

## 10. Шаблон отчёта

В конце каждой задачи публикуй отчёт по шаблону — блок обязателен:

```
## Отчёт: Задача №N (название, версия vX.Y.Z)
- Что сделано: ...
- Файлы: создано / изменено / удалено — список
- Тесты: python -m pytest tests/ -q → <результат>
- VERSION: <старая> → <новая>, CHANGELOG обновлён (да/нет)
- Коммит: <hash> → ветка dev
- ⚠️ Замечания / спорные моменты: <список или «нет»>
```

Если в процессе работы возникла неопределённость, противоречие в требованиях
или потенциальная проблема, которую ты видишь, но можешь продолжить работу —
**не блокируй задачу**, но обязательно укажи это в пункте «⚠️ Замечания /
спорные моменты». Примеры: устаревший комментарий в коде, неоднозначная
трактовка правила, подозрение на скрытый баг, предложение по улучшению
архитектуры.
