# DECISIONS.md — журнал принятых решений

Этот файл — append-only журнал решений проекта SleepTracker: **почему так**, а не
что делать. Роадмап и текущие приоритеты живут в `BACKLOG.md`; здесь —
обоснования. Новые записи добавляются в конец списка с датой принятия решения.

---

## 2026-11-11 — стартовые записи (по результатам аудита проекта)

1. **Формат работы.** Проект ведётся через два чата: AI-менеджер (анализ проекта,
   составление паспортов задач, ревью отчётов) и AI-кодер (исполнение задач).
   Владелец проекта принимает финальные решения и сам выполняет организационные
   действия — merge в `main`, теги, релизы, галочки в `BACKLOG.md`. Агенты в эти
   действия не вовлекаются.

2. **Версионирование.** Единственная точка истины по версии — строка `VERSION` в
   `app.py`. Каждый коммит в `dev` повышает версию (MINOR — новая фича, PATCH —
   фикс/рефакторинг/документация) и сопровождается записью в `CHANGELOG.md` тем
   же коммитом. MAJOR поднимается только по прямому решению владельца. Merge
   `dev` → `main` отдельного бампа не добавляет; тег релиза имеет вид
   `v<VERSION>`.

3. **Замороженный стек.** Стек зафиксирован: Python 3.8.6 (совместимость с
   Windows 7 — домашняя машина владельца), Flask 3.0.3. Flask не обновляется:
   упомянутая в аудите уязвимость PYSEC-2026-2151 не эксплуатируется, потому что
   в приложении не используются сессии. Транзитивные зависимости планируется
   зафиксировать через `constraints.txt` (задача в плане Этапа 1.5).

4. **Ветка разработки.** Разработка ведётся в ветке `dev` (заменила ветку
   `qwen`). PR, merge и теги — ручные действия владельца. Первый тег — v0.8.0
   (релиз после Этапа 1.5); ретроспективные теги на старые версии не ставятся.

5. **`QWEN_RULES.md` → `AGENTS.md`.** Файл правил переименован и переписан по
   двум причинам: агенты автоматически подхватывают файл по имени `AGENTS.md`, и
   это нейтрально к модели — контракт работает для любого AI-кодера. Процессная
   специфика Qwen (окружение coder.qwen.ai и связанное) удалена.

6. **Бэкап базы.** Схема минимального бэкапа: при `POST /save` при смене
   календарной даты выполняется `conn.backup()` (SQLite Backup API — не падает с
   `PermissionError` на Windows, в отличие от `shutil.copy`), ротация 3 копий с
   именами `sleep_backup_YYYYMMDD.db`. Настройка «Хранить Х копий» вынесена в
   BACKLOG (Этап 2).

7. **Android-версия.** Android-приложение — стратегическая развилка, решение
   ожидается через несколько месяцев. Тяжёлые вложения в UI приостановлены до
   этого решения. Адаптивная вёрстка сохранена в плане: у неё двойное назначение
   — удобство на десктопе и работа через мобильный браузер, если Android-версия
   не состоится.

8. **Доступ к репозиторию.** Используется один fine-grained PAT (права Contents:
   Read and write), который выдаётся только AI-кодеру. AI-менеджер читает
   репозиторий анонимно (репозиторий публичный). Токен не сохраняется в файлах,
   коммитах и credential store и не выводится в отчётах.

9. **Аудит как основа плана.** Аудит от 2026-11-11 принят как основа плана
   развития. Диагноз аудита «ORDER BY в SQL критичен» опровергнут экспериментом:
   `compute_state` сортирует входные данные внутри себя, поэтому порядок строк,
   возвращаемых из БД, на результат не влияет. Задача понижена до категории
   «Техобслуживание».

## 2026-11-11 — дополнения (Задача №2, v0.7.3)

10. **Авторство коммитов Кодера.** Коммиты агента подписываются именем
    «Z.ai Agent», email — приватный noreply-адрес владельца (привязан к его
    профилю GitHub: аватар, атрибуция и contributions засчитываются владельцу).
    Отличие агентских коммитов в истории — по имени автора. Отдельный
    GitHub-аккаунт для агента (со своим аватаром) — возможное развитие позже;
    сейчас не заводим ради простоты. Часовой пояс коммитов — Europe/Moscow
    (UTC+3). Шаги начала сессии прописаны в `AGENTS.md`, потому что песочницы
    пересоздаются между сессиями — настройка должна жить в контракте, а не в
    разовой команде.

11. **`import_history.py` удалён из репозитория.** Одноразовый мигратор
    Excel→SQLite использован на старте проекта и своё отработал; восстановление
    возможно из git-истории. Вместе с ним удалён его тест `test_import_csv.py`
    (тесты удалённой фичи уходят вместе с фичей); пункт «Импорт через UI» снят
    с Этапа 3 BACKLOG.

## 2026-11-12 — Этап 1.5: безопасность и полировка (Задача №3, v0.8.0)

12. **Проверка утечек памяти признана нецелесообразной** для текущей
    архитектуры: Flask dev-сервер, объекты живут в пределах запроса, глобальных
    кэшей и фоновых задач нет. Вернуться к вопросу при появлении долгоживущих
    кэшей или фоновых процессов.

13. **Chart.js вендорится локально** (`static/js/chart.umd.min.js`, версия
    4.4.1 — та же, что была на CDN): офлайн-режим, независимость от внешних
    сервисов. Шаблон подключает файл через `url_for('static', ...)`;
    PyInstaller-сборка получает его через `--add-data "static;static"`.

14. **`constraints.txt` генерирует владелец** на целевом Python 3.8.6
    (Windows), а не агент в песочнице (3.12): срез зависимостей должен
    отражать целевое окружение. Файл — минимальное дерево проекта
    (19 пакетов: runtime Flask, dev pytest, build PyInstaller), а не полный
    срез системного интерпретатора; pytest-cov сознательно не зафиксирован
    (в целевой среде не установлен).

## 2026-11-13 — Полировка UX (Задача №4, v0.9.0)

15. **Каркас подтверждений/уведомлений — на нативном `<dialog>`**
    (`showModal()`), а не самописный модальный слой и не системные
    `confirm()`/`alert()`: ноль зависимостей, поддержка в браузерах Win7,
    a11y из коробки (focus trap, Esc), стили — палитра приложения, тёмный
    `::backdrop`. Единый хелпер (`showConfirm` / `showAlert`, API с опциями
    `title` / `message` / `okText` / `danger` / `okOnly`) используется всеми
    будущими фичами (Этап 2 — настройки и бэкапы, Этап 3 — экспорт); новые
    системные `confirm()` в проект не добавляются. Системный `confirm()`
    больше нигде не используется.

16. **Теги ставятся только на выпускаемые релизы;** версии CHANGELOG могут
    не иметь собственного тега: v0.8.0 выходит в составе релиза v0.9.0
    (решение владельца: релизы на «разорванных» версиях допустимы).

## 2026-11-13 — Ghost-разблокировка и UX-мелочи (Задача №5, v0.10.0)

17. **Семантика ghost-памяти пересмотрена по полевому тесту владельца**
    (v0.9.0): вечная молчаливая блокировка лишала возможности повторного
    ввода ночной записи после её удаления (три вектора блокировки в `/save`).
    Оставлена защита по умолчанию + явная разблокировка одной кнопкой
    («Разрешить повторный ввод» → `POST /unlock_night` снимает память
    по вечеру — этим лечатся все три вектора блокировки). Альтернатива
    «убрать механизм совсем» отклонена: защита от молчаливой перезаписи
    слота правкой соседнего вечера сохранена.

## 2026-11-14 — R1-plus: семантика правки и инвариант вечера (Задача №6, v0.11.0)

18. **Пересмотр «варианта A» (утверждён в Этапе 1) по полевому тесту
    владельца:** инлайн-правка через полночь переатрибутировала запись
    на вечер предыдущего дня (две записи «одного отхода ко сну» под одной
    датой) и скрыто метила `deleted_nights` (блокировка вечера, из которого
    ничего не удалялось); воспроизводимость 100%, поведение оказалось
    неожиданным. Новая семантика (R1-plus, утверждена владельцем):
    «правка не меняет вечер» — при неизменённой дате правка через полночь
    роллит дату (0→1: +1 день, 1→0: −1 день), явная смена даты сохраняет
    перенос между вечерами; инвариант «один отбой на вечер» — в каждом
    вечере ровно одна запись, новая заменяет прежнюю (правило владельца:
    ночные пробуждения не учитываются). Ghost-механизм (DELETE-пометка +
    разблокировка) сохранён без изменений; edit-путь больше ничего не
    помечает, очистка вечера при замене пометок не ставит.

## 2026-11-15 — Релизный чек-лист (Задача №7.1, v0.11.1)

19. **Перед созданием Release проверяются пять точек версии:** `VERSION` в
    `app.py`, строка «Текущая версия» в `README.md`, верхняя запись
    `CHANGELOG.md`, футер `BACKLOG.md`, версия в сообщении коммита/заголовке
    PR. Дополняет «правило четырёх точек версии» (AGENTS.md §5) пятой точкой
    на уровне Release: в v0.11.0 строка версии в README осталась 0.10.0 при
    синхронных остальных точках — несоответствие любой из пяти точек
    блокирует Release. **Пост-релизные правки документации выпускаются
    отдельным PATCH-релизом**, а не правкой записи уже опубликованной версии
    (прецедент — v0.11.1, решение владельца от 2026-11-15).

## 2026-11-15 — Пересоздание dev после каждого слияния (Задача №7.2, v0.11.1)

20. **Ветка `dev` пересоздаётся из main после каждого слияния** (решение
    владельца от 2026-11-15): squash-merge создаёт на main новый коммит,
    продолженная dev перестаёт быть потомком main, merge-base остаётся на
    старой базе — трёхсторонний merge видит «одни и те же строки,
    изменённые по-разному», PR получают фантомные конфликты (кейс PR #12:
    7 файлов задач №7/№7.1 при идентичных деревьях). Перед новой задачей —
    `git fetch origin && git checkout -B dev origin/main`; незалитые хвосты
    переносятся cherry-pick; старые коммиты не теряются (Restore branch на
    влитый PR либо `refs/pull/<N>/head`). Заменяет прежнее правило задачи
    №7 (п. B) о продолжении работы в той же ветке.
