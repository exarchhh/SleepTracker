# DECISIONS.md — журнал принятых решений

Этот файл — append-only журнал решений проекта SleepTracker: **почему так**, а не
что делать. Роадмап и текущие приоритеты живут в `BACKLOG.md`; здесь —
обоснования. Новые записи добавляются в конец списка с датой принятия решения.

---

## 2026-11-11 — стартовые записи (по результатам аудита проекта)

1. **Формат работы.** Проект ведётся через два чата: AI-менеджер (анализ проекта,
   составление паспортов задач, ревью отчётов) и AI-кодер (исполнение задач).
   Владелец проекта принимает финальные решения и сам выполняет организационные
   действия — merge в `main`, теги, релизы, галочки в `BACKLOG.md`. Агенты в эти
   действия не вовлекаются.

2. **Версионирование.** Единственная точка истины по версии — строка `VERSION` в
   `app.py`. Каждый коммит в `dev` повышает версию (MINOR — новая фича, PATCH —
   фикс/рефакторинг/документация) и сопровождается записью в `CHANGELOG.md` тем
   же коммитом. MAJOR поднимается только по прямому решению владельца. Merge
   `dev` → `main` отдельного бампа не добавляет; тег релиза имеет вид
   `v<VERSION>`.

3. **Замороженный стек.** Стек зафиксирован: Python 3.8.6 (совместимость с
   Windows 7 — домашняя машина владельца), Flask 3.0.3. Flask не обновляется:
   упомянутая в аудите уязвимость PYSEC-2026-2151 не эксплуатируется, потому что
   в приложении не используются сессии. Транзитивные зависимости планируется
   зафиксировать через `constraints.txt` (задача в плане Этапа 1.5).

4. **Ветка разработки.** Разработка ведётся в ветке `dev` (заменила ветку
   `qwen`). PR, merge и теги — ручные действия владельца. Первый тег — v0.8.0
   (релиз после Этапа 1.5); ретроспективные теги на старые версии не ставятся.

5. **`QWEN_RULES.md` → `AGENTS.md`.** Файл правил переименован и переписан по
   двум причинам: агенты автоматически подхватывают файл по имени `AGENTS.md`, и
   это нейтрально к модели — контракт работает для любого AI-кодера. Процессная
   специфика Qwen (окружение coder.qwen.ai и связанное) удалена.

6. **Бэкап базы.** Схема минимального бэкапа: при `POST /save` при смене
   календарной даты выполняется `conn.backup()` (SQLite Backup API — не падает с
   `PermissionError` на Windows, в отличие от `shutil.copy`), ротация 3 копий с
   именами `sleep_backup_YYYYMMDD.db`. Настройка «Хранить Х копий» вынесена в
   BACKLOG (Этап 2).

7. **Android-версия.** Android-приложение — стратегическая развилка, решение
   ожидается через несколько месяцев. Тяжёлые вложения в UI приостановлены до
   этого решения. Адаптивная вёрстка сохранена в плане: у неё двойное назначение
   — удобство на десктопе и работа через мобильный браузер, если Android-версия
   не состоится.

8. **Доступ к репозиторию.** Используется один fine-grained PAT (права Contents:
   Read and write), который выдаётся только AI-кодеру. AI-менеджер читает
   репозиторий анонимно (репозиторий публичный). Токен не сохраняется в файлах,
   коммитах и credential store и не выводится в отчётах.

9. **Аудит как основа плана.** Аудит от 2026-11-11 принят как основа плана
   развития. Диагноз аудита «ORDER BY в SQL критичен» опровергнут экспериментом:
   `compute_state` сортирует входные данные внутри себя, поэтому порядок строк,
   возвращаемых из БД, на результат не влияет. Задача понижена до категории
   «Техобслуживание».
