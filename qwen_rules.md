# Правила работы Qwen Coder с проектом SleepTracker

Этот файл описывает предпочтительный подход к разработке. Читай его перед началом работы.

## 🎯 Главный принцип

**Защищай стабильность проекта, но не бойся делать необходимые изменения.** 
Если задача требует изменений в "защищённых" частях — делай их, но:
- Объясни в коммите, почему это необходимо
- Убедись, что все тесты проходят после изменений
- Если сомневаешься — спроси перед изменением

---

## 1. Ветвление Git

Вся разработка ведётся в ветке `qwen` (или `feature/название`).
Прямой push в `main` ЗАПРЕЩЁН.
Перед началом НОВОЙ задачи (если ветка создана заново): `git pull origin main`.
В процессе работы над задачей: развивай ветку `qwen` независимо, НЕ делай `git merge origin main` в `qwen` без прямой команды владельца.

---

## 2. Тестирование

✅ **Делай:**
- Перед коммитом: `python -m pytest tests/ -q`
- Если тесты падают — сначала попробуй починить код
- Если тест устарел или ошибочен — предложи его исправить

📌 **Важно:** Тесты — это инструмент качества, не догма. Если тест мешает исправить баг — Сообщи, обсудим.

---

## 3. Ядро логики (compute_state, evening_anchor, level_of, night_key, effective_evening)

🛡️ **Эти функции стабильны и хорошо протестированы.**

✅ **Делай:**
- Читай их код перед задачами, связанными с расчётом штрафа
- Если видишь очевидный баг — Сообщи с примером
- Если задача требует изменений — делай, но:
  - Добавь новый тест для покрытия изменения
  - Убедись, что старые тесты проходят
  - Опиши в коммите, что и зачем изменил

❌ **Не делай:**
- "Оптимизацию для красоты" без необходимости
- Изменение поведения без обновления тестов

---

## 4. Бизнес-правила (константы)

📊 **Текущие значения:**
- `IDEAL_MINUTES = 1380` (23:00)
- `MAX_BURN_PER_DAY = 120` (максимум сжигания за вечер)
- `RED_THRESHOLD = 600` (штраф для красного цвета)

✅ **Делай:**
- Используй эти константы в коде
- Если задача требует изменения — меняй (например, через config.json в будущем)

📌 **Важно:** Эти значения могут быть изменены по требованию пользователя. Не хардкодь их в логику.

---

## 5. Работа с backlog.md

✅ **Делай:**
- Читай файл перед началом работы — там текущие приоритеты
- После выполнения задачи — поставь галочку `[x]` в backlog.md
- Если задача выполнена частично — отметь это

 **Не делай:**
- Добавления новых задач без команды
- Изменения структуры файла

---

## 6. Окружение coder.qwen.ai

✅ **Делай:**
- Перед тестами: `pip uninstall -y libtmux` (конфликт с pytest 9.x)
- Токен GitHub передаётся в чате — используй для git операций
- После `git push` выполни `git pull` (чтобы не терять доступ)
- Если `~/.git-credentials` пуст — восстанови токен

---

## 7. Технические стандарты

🔧 **Стек:**
- Python: 3.8.6+ (совместимость с Windows 7)
- Flask: версии из requirements.txt (зафиксированы)
- Chart.js: для графика (CDN)
- Тёмная тема: цвета `#1a2130`, `#2a3550`, `#3ecf7a`, `#f06a6a`
- Русские дни недели: Пн, Вт, Ср, Чт, Пт, Сб, Вс

✅ **Делай:**
- Сохраняй тёмную тему и русские дни недели
- Используй фиксированные версии библиотек

---

8. Приоритеты при конфликтах

Если задачи противоречат друг другу или правилам:
1. **Безопасность данных** > стабильность кода > новые фичи
2. **Тесты должны проходить** (или объясни, почему это нормально)
3. **Сообщи о конфликте** — не игнорируй правила молча

⚠️ **Спорные моменты и замечания:**
Если в процессе работы возникает неопределённость, противоречие в требованиях, 
или ты видишь потенциальную проблему (но можешь продолжить работу) — 
**не блокируй задачу**, но обязательно упомяни это в финальном отчёте 
отдельным пунктом "⚠️ Замечания / спорные моменты". 
Примеры: устаревший комментарий в коде, неоднозначная трактовка правила, 
подозрение на скрытый баг, предложение по улучшению архитектуры.
